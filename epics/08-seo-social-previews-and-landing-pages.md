## Outcome

Shared wrkgn links show a useful preview on social and chat platforms. Search engines get distinct titles and descriptions, sitemap freshness hints and basic structured data. Fonts are self-hosted. Category and audience landing pages give crawlers and visitors indexable entry points beyond the date-ordered list. Project pages link to related projects.

## Motivation

The maintainer began sharing wrkgn on 2026-11-18. A review of production that day, with counts re-measured on the local export on 2026-11-20, found:

- `robots.txt`, a sitemap, canonical links, per-project meta descriptions, `noindex, follow` on search/filter results, trailing-slash 301s and real 404 statuses are already in place. HTTP→HTTPS 301 is done by Cloudflare "Always Use HTTPS", not origin code.
- The sitemap holds about 17,549 URLs (16,982 projects plus 567 list pages, ceil(16982/30)), well under the 50,000-per-file split, which stays as is.
- At review time there were no Open Graph or Twitter card tags and no preview image (both are now implemented), so shared links render without a title, description or image on most platforms.
- Project titles are only the project name (`mib · wrkgn`). Every list page, including `/projects/page/N/`, uses the title `Explore projects · wrkgn`.
- Project meta descriptions use the full summary; about 62% of projects exceed the roughly 155 characters search results show.
- Sitemap entries have no `<lastmod>`.
- There is no structured data.
- The Google Fonts stylesheet is render-blocking and adds two third-party connections.
- Filtering exists only as query-string results marked `noindex`. There is no indexable page per category or audience, and project pages link only to other projects by the same builder.

Search Console and Bing Webmaster Tools registration, sitemap submission and Cloudflare dashboard settings (Crawler Hints, bot handling) are maintainer tasks outside this epic.

## Product decisions

- All metadata derives from the public snapshot and fixed server configuration. No pipeline, LLM or HN activity, and no new private data in the snapshot.
- `--public-origin` remains the single source for absolute URLs in tags, structured data and sitemaps.
- The schema 6 snapshot already includes taxonomy labels and descriptions, project labels, `latest_shared_at` and builders. Prefer work that needs no snapshot schema change. If a phase needs one, stop and report the proposed change instead of implementing it.
- Generated text stays factual and attributed in the same way as visible page content. Don't invent claims in metadata that the page does not show.
- Search and filter result pages stay `noindex, follow`. New landing pages are canonical, indexable, ordinary HTML pages, separate from the query-string filter routes.
- Preview image: one static, branded 1200×630 PNG served as a hashed asset. The maintainer approved a generated image, checked in as `crates/wrkgn-web/assets/src/og-image.png`; its generator is `crates/wrkgn-web/assets/tools/og-image.swift` (macOS only, run manually, not part of any build). Per-project generated images are out of scope.

## Scope

### Phase 1: Asset pipeline

1. **Manifest:** extend `crates/wrkgn-web/assets/build.mjs` to copy and content-hash the approved PNG preview image (`src/og-image.png`, generated by `tools/og-image.swift`) into `dist/`, recording it in `manifest.json` (the manifest is still written last). The manifest stays a flat key → filename map. Keys must be lowercase identifiers matching `[a-z][a-z0-9_]*`, because `build.rs` derives URL constants from `key.to_uppercase()` (for example `og_image`, later `font_dm_sans_400`). Font files and their license text are added in Phase 3. License files are copied to `dist/` and kept in the repository, but are not embedded or served.
2. **Embedding:** change `crates/wrkgn-web/build.rs` to iterate manifest entries instead of the fixed `["script","style","icon"]` keys with hardcoded MIME types. Derive the MIME type from the file extension and add `image/png` and `font/woff2`. Keep the filename safety assertions and enforce the key rule above. Generate URL constants for the new entries (for example `OG_IMAGE_URL`) alongside the existing `SCRIPT_URL`, `STYLE_URL` and `ICON_URL`.
3. **Tests:** in `crates/wrkgn-web/tests`, `/assets/<hash>.png` returns 200 with the correct `Content-Type` and the Asset cache class headers (see `CacheClass::Asset` in `src/server.rs`); Phase 3 adds the same check for `.woff2`.
4. **Deploy note:** hashed assets referenced from cached HTML (the preview image, fonts) need `scripts/deploy.sh --purge` when they change, so edge-cached HTML points at the new hashes. `docs/hosting.md:55` already documents `--purge` for rendering changes; extend that sentence to mention hashed image and font changes.

`npm run build --prefix crates/wrkgn-web/assets`, `cargo fmt --all --check`, `cargo clippy --workspace --all-targets`, `cargo test --workspace` pass. Locally, request the new asset URLs from `wrkgn-web` and inspect headers. Report the results before Phase 2. Commit nothing unless the maintainer asks.

### Phase 2: Metadata on existing pages

1. **Open Graph and Twitter cards** in `templates/layout.html`, populated per page through `render::layout`:
   - `og:title`, `og:description`, `og:url` (the canonical URL), `og:site_name` (`wrkgn`), `og:type` (`website` for lists, `article` for project pages), `twitter:card`, and the image tags. The maintainer approved a generated 1200×630 image (`crates/wrkgn-web/assets/src/og-image.png`, produced by `crates/wrkgn-web/assets/tools/og-image.swift`). Every page with social tags emits `og:image` (from `OG_IMAGE_URL`, made absolute with `--public-origin`), `og:image:type`, `og:image:width`/`og:image:height`/`og:image:alt`, `twitter:image` and `twitter:card` = `summary_large_image`.
   - Error pages: `render::error` builds its own head and keeps it without any OG or Twitter tags. Add a test.
2. **Distinct titles.** Lengths count Unicode scalar values (`chars()`), never bytes. The en dash is allowed.
   - Homepage: a descriptive title that names what the site is, use `Projects shared on Hacker News · wrkgn` unless the maintainer chooses other wording.
   - `/projects/page/N/`: include `Page N`.
   - Project pages: `<name> – <short description> · wrkgn`, about 60 characters in total including the ` · wrkgn` suffix. Algorithm: if the description begins with the project name, compared case-insensitively (common: about 2,110 of 16,982 projects; 2,068 case-sensitive), strip that prefix and any following separator punctuation and whitespace first; truncate the remainder at a word boundary so the whole title fits the budget; if nothing useful remains, use the name alone. The 131 unnamed projects use the existing `title()` fallback in `render.rs` ("Unnamed project") as the name part and follow the same algorithm, without prefix stripping.
   - Keep the `<h1>` and visible content unchanged.
3. **Meta description length:** truncate to about 155 characters at a word boundary, with an ellipsis, for `<meta name="description">`, `og:description` and `twitter:description` only. Visible descriptions stay full. List pages keep a fixed description; page N may add `Page N`. Tests use real-length strings (a majority of projects exceed the limit), not short toy text.
4. **Sitemap `<lastmod>`:** on project URLs only, from the project's `latest_shared_at`, in W3C format at UTC. `latest_shared_at` is the latest sharing date, not a page modification time; this is accepted as a freshness hint. Omit it on list pages (and on landing/index pages added in Phase 4). Keep the existing ordering, the 50,000 limit and the index behavior. Don't add `changefreq` or `priority`; search engines ignore them.
5. **Structured data** as one JSON-LD `<script type="application/ld+json">`:
   - Homepage: either `WebSite` with `name` and `url` only, or nothing. No `SearchAction`: Google retired the sitelinks search box in 2024, and `/?q=` is disallowed in `robots.txt` and `noindex`.
   - Project pages: `CreativeWork` (`SoftwareApplication` only when the page states it is software) with `name`, `description` and `url`. `latest_shared_at` is not a modification date; do not emit it as `dateModified`. Emit `datePublished` only as the minimum `shared_at` over `Detail.mentions` (`crates/public-snapshot/src/lib.rs`, ordered newest first, so do not rely on the first row); omit dates if there are none. `author` is a `Person` per listed builder with `name` set to the HN username and `url` `https://news.ycombinator.com/user?id=<name>` (percent-encoded). Listing follows the page's existing "shared by" convention and does not claim verified ownership.
   - Serialize with `serde_json` and escape `</` so source-derived text cannot close the script element. Add a test with a hostile description.
6. **Enhanced navigation note:** `syncHead` in `assets/src/main.ts` swaps only title, canonical, robots and description after in-page navigation. OG tags and JSON-LD may go stale after modal or list navigation; this is accepted because crawlers and preview bots load full pages. Add a code comment saying so, and do not extend `syncHead` to cover them.
7. **robots.txt review:** `Disallow: /?` stops crawlers from fetching filter/search URLs, so they never see the `noindex` on those pages. Tracking-parameter URLs on the homepage (for example `/?utm_source=x`) 301 to `/` but are also blocked, while project URLs with tracking parameters return 200 with a canonical and are not blocked. Keep the current rules unless a concrete problem is found (for example, Search Console reporting "Indexed, though blocked by robots.txt"). Record the reasoning in `docs/development.md` either way. If changing, block only the parameterized filter/search routes, keep the sitemap line and add a test.
8. **Tests** (in `crates/wrkgn-web/tests`, offline fixture snapshot):
   - OG, Twitter and JSON-LD tags are present with absolute canonical URLs on the homepage, a list page and a project page. Search/filter results keep `noindex`. Error pages have no OG tags.
   - Title and description truncation at word boundaries: multibyte text, missing names, unnamed projects (fallback name, no prefix stripping), descriptions that begin with the name (including differing case), real-length descriptions.
   - Sitemap `<lastmod>` on project URLs only, and unchanged URL sets.
   - JSON-LD author URL, absence of `dateModified`, `datePublished` as the minimum mention date, and HTML/script escaping of source-derived text in every new attribute and block.

### Phase 4: Category and audience landing pages

Category pages shipped first and passed the maintainer check; audience pages then reused the same code paths. Audience data is sparse (57% of projects have no audience label and the smallest audience has about 67 projects), so audience pages are not expected to rank strongly; they are included for completeness and navigation.

1. **Routes:** `/categories/<slug>/` and `/audiences/<slug>/`, paginated as `/categories/<slug>/page/N/` like `/projects/page/N/`. Plus index pages `/categories/` and `/audiences/` listing each label with its description and project count. Non-canonical forms (missing trailing slash, `page/1/`, leading zeros) redirect as existing routes do. Unknown or empty labels return 404 (there are no empty labels today); test it.
2. **Content:** each landing page shows the label as `<h1>`, the taxonomy description from the snapshot as a short intro, the project count, and the same cards and pagination as the main list, newest first. Distinct title, description, canonical, OG tags and `CollectionPage` JSON-LD. No new editorial text beyond the taxonomy descriptions unless the maintainer supplies it. Counts derive from in-memory discovery data; no snapshot schema change.
3. **URL model (`src/discovery.rs`, `assets/src/canonical.ts`):** `State`, `read_state`, `state_url`, `resolve` and path paging only know `/`, `/projects/page/N/` and `/?…`. A landing page whose category sits in `State` would 301 to `/?category=x`, and its pagination links and `data-list-url` would point at `noindex` query URLs. Add a fixed-criterion/base-path mode to `State`, `read_state`, `state_url`, `resolve` and the listing's page links, so a landing page canonicalizes to its own path and pages under it. Mirror the mode in `canonical.ts`, `assets/tests/canonical.test.mjs` and the shared fixture `crates/wrkgn-web/tests/fixtures/canonical-urls.json`, which both the Rust (`tests/discovery.rs`) and TypeScript suites consume.
4. **Server routing (`src/server.rs`):**
   - The trailing-slash redirect in `handle` matches only `/projects`; extend it to the landing prefixes.
   - Extend `list_path` and the render `Semaphore` permit (503 with `Retry-After` when saturated), both list-only today, to landing routes.
   - Landing pages use the Public cache class, not Filtered. The class is currently chosen by `has_criteria()`, so the fixed landing criterion must not count as a query criterion for this purpose.
   - Keep the 30-per-page size and the at-most-one-page allocation bound. No edge cache rule change is needed: the Cloudflare rules in `docs/hosting.md` match hostnames, not paths.
5. **Client (`assets/src/main.ts`):** `main.ts` calls `history.replaceState` with `data-list-url` on load, so landing pages emit their own landing URL there. Filter, sort and search controls build `/?…` URLs. Behavior on a landing page: using a control navigates to the equivalent `/?category=…` query result (`noindex`), with the sidebar showing the landing's label checked; `[data-clear]` goes to `/`. Document this in `docs/development.md`. Category tags on cards and category and audience tags on project pages were plain `<span class="tag">` text, so tag links are `<a>` elements to the landing pages (cards show category tags only). On cards they sit beside, not inside, the card's `data-project-link`, so the modal enhancement does not intercept them. Tag links clicked inside the project modal perform full navigation. Test back/forward, pagination, sort, search and clear from landing pages, and modal open/close behavior inside landing pages.
   - Decision (maintainer): `/?category=<x>`, and any query filter or search, keeps its current behaviour as a `noindex, follow` result canonicalising to `/`. It does not redirect or canonicalise to `/categories/<x>/`. Reasoning: `robots.txt` already disallows `/?`, interactive filtering stays on query parameters, and the landing pages are separate SEO entry points reached through navigation and tag links rather than through filter state.
6. **Indexing:** `/categories/`, `/audiences/` and page 1 of each landing page are indexable and in the sitemap. Page 2 and later are self-canonical with `index, follow` and are not in the sitemap. Query filters stay `noindex, follow`.
7. **Sitemap:** fixed order: list pages, then landing/index pages, then projects. No `<lastmod>` on landing or index pages. Test the 50,000 split boundary with a fixture.
8. **Navigation:** add "Categories" and "Audiences" links to the sidebar/footer navigation.
9. **Tests:** routing, 404 and redirects for landing pages (including empty/unknown labels); pagination; canonical/robots correctness (page 1 and 2+ landing pages, query filters `noindex`); State/canonical fixture cases in both suites; tag links; control behavior from landing pages; sitemap contents, order and split; saturated-render 503; cache class; modal behavior unaffected.

### Phase 5: Related projects

1. **Section:** add a short section with the visible heading "Related projects" on project pages, up to six projects. The code already uses `related`/`RelatedProject` for "same builder" (`crates/wrkgn-web/src/render.rs`, template `.related-list`), so name the new data `similar_projects` and use "Related projects" only in visible text. Score = shared categories weighted by rarity (inverse category frequency across the snapshot), plus shared audiences as a secondary score, with recency (`latest_shared_at`) as the final tiebreak. Exclude the current project and projects listed under "Also shared by this builder". Require a minimum score; with 15 categories and the two largest (developer-tools 4,816, ai-automation 4,556) covering most projects, a rule that a match on only one of those two does not meet the minimum is allowed. Render the section only when results exist (about 329 projects have no category). Keep "Also shared by this builder" a distinct section.
2. **Determinism and cost:** results are deterministic for a given snapshot. Precompute on snapshot load; do not compute per request. (`same_builder_projects` in `crates/public-snapshot/src/lib.rs` runs per-request SQL with no `LIMIT`, so don't copy that pattern.)
3. **Measurement:** no full-snapshot memory baseline is recorded (`docs/implementation/epic05.md` and `docs/hosting.md` call the limits provisional), so Phase 5 records its own before/after baseline: snapshot load time and memory with a production-sized snapshot, in `docs/implementation/` or `docs/development.md`. A SIGHUP reload holds two snapshots at peak; measure that too.
4. **Quality check:** manually review related results on a sample of about 20 project pages and report them before tuning the minimum score.
5. **Tests:** determinism, exclusions, minimum score, rarity weighting, no-category projects, tie-breaking.

## Acceptance criteria

- A project URL pasted into a link-preview debugger (for example, the opengraph.xyz or LinkedIn Post Inspector tools) shows the project title, description and the wrkgn image. The maintainer checks this after deployment.
- Homepage, list pages, project pages and landing pages each have a distinct title and a description of 155 characters or fewer.
- Project sitemap entries carry `<lastmod>` from `latest_shared_at`; list and landing/index pages have none. Page 1 of each landing page and the index pages are in the sitemap.
- No third-party font requests remain, and the CSP header contains neither Google host.
- JSON-LD validates in Google's Rich Results Test or the Schema.org validator for one page of each type (maintainer, after deployment).
- Category and audience landing pages are reachable through ordinary links, indexable and paginated; query-string filter pages remain `noindex`.
- Related projects are deterministic per snapshot, and their load-time and memory cost is measured and recorded.

## Validation

Offline fixtures and a local server for automated and manual checks. Production checks (link-preview debuggers, structured-data validators, Search Console coverage, cache behavior of new routes and assets) happen after the maintainer deploys. Every phase that changes HTML, head tags or the sitemap must be deployed with `scripts/deploy.sh --purge`, because public HTML and the sitemap are edge-cached for 7 days. Link-preview services cache too, so the maintainer re-scrapes after deploy.

Risks: staging `next.wrkgn.com` serves the same canonical, `og:url` and sitemap URLs on the production origin and has no `noindex`; accepted as long as staging is not linked or indexed.

## Boundaries

No snapshot schema change without stopping to report first. No changes to collection, extraction, review or export semantics. No new editorial or LLM-generated copy, and no per-project images. No analytics or tracking scripts. Search Console, Bing Webmaster Tools and Cloudflare dashboard settings are maintainer tasks.

Out of scope: one project in the local export has six categories although the taxonomy documents zero to five per mention. This epic does not investigate or fix it.
